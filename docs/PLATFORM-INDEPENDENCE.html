The question behind the ninth piece of work

Can Pi Central run anywhere other than a Mac?

Probably yes. That is the whole answer, and this page is the long version — the one to come back to when the pieces have drifted apart again.

Written 28 November 2026 Nothing here is ported yet Two questions decide it

Probably yes, and it is a backend swap rather than a rewrite.

Every session Pi Central runs sits inside a sandbox. That sandbox is a Mac-only tool called Safehouse. The question this work answers is whether depending on that tool means depending on a Mac — and it does not. The dependency is one swappable part, not the product around it.

Nothing has been ported yet

Every commit so far is documentation, issue tracking, or a check wired into CI. No product code has changed. The decision record is still marked proposed, which is deliberate — see what is still unproven.

Two layers, not one

This is the correction that took the longest, and everything else depends on it.

There are two different things people mean by "the sandbox", and they live at different depths.

  • The kernel boundary. The operating system itself refuses the operation. On a Mac this is Seatbelt. A process cannot get past it by asking differently.
  • The policy engine. A trusted program outside the sandbox inspects each request before passing it through, and refuses the ones a rule forbids. It answers questions like "may this session connect to that host". The sandbox never sees a refusal it could argue with.

The sandbox tool Pi Central uses today is a kernel boundary. The tool under consideration for Linux, called Box, provides both layers — a kernel boundary and a policy engine. The original research compared only the policy language and concluded things about security that a policy language cannot support. That comparison was wrong, and the image below is what corrected it.

What the boundary must do

The decision defines the sandbox as three parts. The third was the discovery.

  1. 1

    The command line

    The concrete invocation that starts a session under the boundary. The obvious part.

  2. 2

    A policy where a prohibition beats a permission, whatever the order

    The current sandbox decides conflicts by last matching rule, which is why a large amount of existing code exists purely to restate narrower permissions at matching specificity. That is a whole class of defect, and a replacement must not reintroduce it.

  3. 3

    A statement of which file operations the policy actually covers

    Not "we wrote denies" but "these denies bind the agent's own tools, and these bind only a shell". A backend that stays silent about this is not a candidate, however well it runs.

What we have decided

The decision record is written. Its answer is narrower than the question, on purpose.

A second sandbox backend is worth defining. That part is settled and argued in docs/decisions/0020-a-sandbox-is-a-defined-boundary.md.

Which backend is not settled, and the record refuses to guess. Box is the candidate the research examined; it is not the decision. Naming it now would mean choosing ahead of two measurements that do not exist yet — which is the same mistake the research already made twice, and recorded both times.

Instead the record sets an admission test: seven requirements a future backend must satisfy, each of which can fail. A candidate is judged against it rather than argued about.

Two approaches are declined, not deferred

ApproachWhy it is not on the table
Declined
Adopt Box today		 Premature. Two decisive measurements are missing, and deciding ahead of a measurement is precisely the error the research already corrected itself for.
Declined
A degraded mode with no isolation		 The tempting shortcut: run sessions unsandboxed elsewhere and label them. It ships an unsafe session under a label everyone quickly learns to ignore. Worse than not porting.
Chosen
Define the boundary, name no backend		 What today's evidence supports. It unblocks the work that does not depend on the missing measurements, without pre-committing to an implementation.

What is still unproven

Two questions. Both are commands, not design arguments. Until the first is run, the honest state is "probably feasible, and feasibility unproven".

The questionWhy it decides everything
Does the agent program start inside a box on Linux? If it cannot start, nothing downstream matters. If it starts, the port is real.
Does a started box refuse a unix-socket connection? It is the one protection with no equivalent form in the new policy language. If it cannot be expressed, the port loses something we have today.

A warning the research earned the hard way

An upstream document says the agent program does not run on Linux. That sentence is out of date — the code that would have made it false was changed four days before the document was last edited.

Out of date is not the same as "works". The first draft of the research repeated that sentence as fact and let it drive a recommendation to rule the whole approach out. Both were wrong.

How large the work is

An earlier summary said the port's cost was "four platform checks". That counted the decisions and missed the mechanism. Measured properly:

2platform checks in product code — where a platform would be asked a question
14product modules that name the current sandbox tool
5of those that own the boundary, plus one spawn site
1,243lines in those five files

So the honest sentence is: two platform decisions, and one boundary implemented against one backend across about twelve hundred lines. A backend swap of real size — not two lines, and not a re-architecture.

What keeps it honest

Six runnable checks assert the research's claims. All six now run automatically, split by what each actually needs rather than by convenience.

Where it runsWhat it asserts
Every push to the repository That a configured credential wins over the route's variable; that the "does not run on Linux" line really is out of date; that the two copies of the Linux probe are identical.
The portability probe, on request That the deny rules translate; that a policy engine is not a kernel boundary; that the box has no keychain source. These need an installed box, and three read its binary.

The probe workflow now fails if a claim the decision rests on has gone stale. That is the difference between a claim and a quotation.

What happens next

  • Run the probe on a hosted runner. One command, and its outcome is what turns the plan into a decision.
  • Read the outcome as one of three things: it starts — the stale line was stale in fact; it aborts on a memory error — executable memory is still refused; the host refuses the cage — and that says nothing about the agent program at all.
  • Close the decision record once both questions answer. It moves to accepted or rejected. It cannot be half-accepted, which is why it stays proposed now.
  • Then, and only then, build the backend interface.
